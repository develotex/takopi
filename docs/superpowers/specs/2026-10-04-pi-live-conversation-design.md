# Pi live conversation in Takopi — design (2026-10-04)

## User intent and acceptance

In one Telegram topic, a Pi task can run for hours while the user asks questions or requests a status update and receives a prompt answer without cancelling or waiting for that task. New constraints/information sent in that topic are durably received, passed to the main Pi session at a safe checkpoint, and explicitly acknowledged when actually considered. The user must be able to tell apart **received**, **delivered to Pi**, and **considered**. The main task, running tools, and detached subagents must not be cancelled just because a message arrives. A quick answer cannot claim to know unrecorded thoughts, a pending tool result, or an unfinished subagent result.

This feature is for the Pi engine in the develotex/takopi fork, targeting `local-dev`. Other engines keep their existing behavior. Existing continuation/topic/session resolution, `/new`, `/cancel`, and explicit queued-turn semantics must remain intact. No Pi core fork or changes to Pi are required.

## Architecture and boundaries

- **Main session:** Takopi owns a long-lived Pi RPC subprocess for an active session, using the installed Pi `--mode rpc` protocol. One owner per Pi session; parse JSONL by byte LF, continuously drain stdout and stderr, correlate RPC responses by ID, and stream session events into Takopi's existing progress/final rendering. `agent_settled` is the completion boundary, not just `agent_end`. The existing one-shot Pi runner remains available as a compatibility/fallback path for sessions that have no live conversation enabled; no silent fallback during an active RPC run.
- **Telegram routing:** Resolve the same topic/session/resume scope currently used by the scheduler, and only offer live handling if a Pi task for that exact scope is active. Other topics and engines continue independently. Ordinary messages during an active run are accepted immediately rather than enqueued as another full run. Commands, explicit replies to a different resume token, file directives and media follow their existing routing unless explicitly supported and tested. Inactive topics retain normal behavior.
- **Quick responder:** A separate short-lived Pi session answers questions in the *same* Telegram topic, grounded in a bounded snapshot: original task, durable user messages, completed/public assistant output, and recorded progress (including async run IDs/status when available). Never use the main session's writable JSONL path for this process. Deny editing, shell, delegation and side-effectful tools; ideally no tools at all unless a tightly scoped read-only source is needed. Do not inject its answer or internal transcript into main Pi context; only the user's original information is eligible for delivery. A status answer is an evidence-backed summary, not speculation about current model reasoning. Time out/fail visibly without disrupting the main task.
- **Durable inbox:** Persist user messages and stable Telegram identity/scope under Takopi state with monotonic ordering and deduplication. Never write secrets from process state into this record. Message lifecycle: `received` (durably stored), `submitted` (RPC command accepted/queued), `delivered` (observed in the main session's message stream), `considered` (explicit main-agent acknowledgement of how it affects work, or why it does not), or `failed/deferred` with reason. A successful RPC `steer` response alone is **not** proof of delivery or consideration. Check pending messages before the main result is marked final; if one races with settlement, resume the same session with a follow-up rather than silently discard. After restart, reconcile message IDs and main session entries before retrying to avoid duplicate user turns; if delivery is uncertain, show it as uncertain instead of falsely claiming exactly-once application. Keep the inbox and resume mapping durable across restart.
- **Delivery checkpoint:** Send queued new information to Pi with RPC `steer` while running, or as a normal continuation after it settles. `steer` waits for the current assistant turn and tool calls; it must never invoke `abort`. Foreground subagent calls can delay consideration; detached children continue independently and do not automatically receive the update. The main agent should evaluate how the update affects in-progress work, stale results and any child that needs deliberate steering. Explicit acknowledgement can be emitted through normal assistant text or a structured bridge event; do not infer `considered` solely from the first assistant message after injection.
- **Message classification/UX:** While active, a message can contain both a question and a constraint. Treat constraints, corrections and new facts as potentially relevant to the main task and store them before replying; the quick answer says whether the new information has merely been received, delivered or considered. Pure questions/status requests are answered by the quick responder without changing main task. When classification is ambiguous, ask rather than silently update main work. An explicit control for 'pass this to the task' should exist as a deterministic escape hatch. Progress and quick answers share the Telegram topic but must have distinct replies/references and must not overwrite each other's message. Backpressure/rate limits bound concurrent quick responders per topic.

## Safety and failure semantics

RPC child death: mark current run interrupted/unknown, retain inbox, keep topic association, and offer recovery from the persisted Pi session after checking state; do not silently resume tool side effects. Telegram delivery failure does not imply the user message was not stored. A submitted steer is not acknowledgement; no 'considered' status without main-agent evidence. Avoid concurrent writers to the same session file/worktree. Observe original user-message ordering even if quick answers complete out of order. Never expose the full private session, tool arguments, credentials, or unrelated topic data to the quick responder or another user. Preserve explicit `/cancel` behavior (cancellation only on intentional command).

## Validation

Unit/integration tests with a fake RPC Pi subprocess: two Telegram messages during a running tool; immediate status answer from a separate session; mixed status+constraint; delayed foreground tool; detached child unaffected; no duplicate application across retries/restart; lifecycle states and racing `agent_settled`; failed RPC/Telegram reply; session/topic isolation; `/cancel`, `/new`, replies to other tokens, non-Pi engine and inactive-topic regressions; resource cleanup and timeouts. Exercise a real installed Pi RPC process in a local smoke test, including queued steer, message events and resumption. Run `just check` before commit. Obtain two independent reviews (fresh Viktor and Devin review), resolve findings, verify again, then push `victor/pi-live-conversation` and create a Russian-language PR targeting `local-dev` with cause → product solution → implementation, explicit limitations and Manual testing checklist. No deployment/restart implied by the PR.

## Staging

Prefer a narrow opt-in for Pi live mode so the existing one-shot bridge remains functional while the new runner and Telegram route are tested. Success criterion: while a long task continues, a status question gets a fast, truthful answer; a constraint gets durable receipt and later explicit consideration; neither operation cancels the original work. If the live mode cannot preserve an existing Takopi continuation/session contract, stop rather than weakening isolation silently.
